E1. THE FEEDBACK LOOP: ONE 62-MINUTE SERIAL SUITE UNDER ONE LOCK
======================================================================
EXISTS
  - tests/conftest.py:41 SLOW = {...}: a hand-kept list of ~48 tests (marked from
    a 2026-10-16 timing of 5 voxel files + test_mpm + hygiene, 202 tests, 366 s).
    pytest_collection_modifyitems at :152 adds the mark. Only those 7 files were
    timed; the other ~207 files have no slow marks, so "-m 'not slow'" over
    tests/ is far from fast. The decisions log reports "FAST 161" (14a end
    check): a set of files, not a pytest tier.
  - Full suite: 4911 tests, ~62 min, run serially inside "flock test.lock
    <cap.sh> python3 -m pytest" (tools/stepcheck.sh:117-125, tools/split/gate.sh:25).
  - cap.sh (WORK/cap.sh): systemd-run memory cap 2500 MB per run plus a CPU
    temperature gate (waits up to 3 min if Tctl >= 88 C).
PROBLEM
  - Nothing runs in parallel. 16 cores, one pytest process. xdist is installed
    and unused. Each lane's "run the tests" is a 60-minute lock hold or a
    hand-picked list (TESTS=...), so lanes pick wrongly: either too little
    (missed regressions found at the end check) or too much (queue).
  - The SLOW list is stale: it was measured on base16 and has no entry for the
    ~100 test files added since (wave 12-15). Drift means "fast" quietly grows.
  - Staleness is silent: nothing fails when a fast test becomes slow.
  - The cap (2.5 GB) and 14 GB RAM bound parallelism: 4 workers x 2.5 GB = 10 GB
    on a machine that already shows 12 GB used (lab runs, editor, browser).
    So "just -n 16" is wrong; the realistic win is -n 3 to 4 with a per-worker cap.
BETTER (a three-tier loop, all derived from one measurement)
  T0 SMOKE (<= 60 s): import every module, test_module_hygiene, test_switch_ledger,
     the four never-slow exactness guards (compiled == plain, bit for bit), and
     one "tick the tiny world N times and compare a hash" test. Run by every lane
     after every edit. No lock (see E3).
  T1 FAST (<= 8 min with -n 4): everything not marked slow. Per-lane: run only the
     tests that import the files the lane touched (see "affected tests" below)
     plus T0. This is what a lane runs before it reports done.
  T2 FULL (the 62 min, now ~20 min with -n 4 if the slow tests balance): only at
     wave end, only by the orchestrator, plus golden --all.
  Mechanics:
   1. Generate the tiers from DATA, not by hand: run once with --durations=0
      (the wave end check already does this) and have tools/split/slowlist.py
      (exists) write tests/slow_tests.json (node id -> seconds). conftest loads
      it. Regenerated at every wave end by the orchestrator, committed. Tier
      thresholds: fast <= 5 s per test, slow > 5 s (the old 90 s budget was per
      FILE group, not a threshold).
   2. Add a failing check that a test file newer than the timing file with no
      timing entry is reported (not failed) so new heavy tests get seen.
   3. "Affected tests": tools/split/deps.py already builds an import graph
      (deps.json). Map changed src file -> test files that import it
      (transitively one hop) -> run those first. A change to will.py or sim.py
      touches nearly everything (then T1 whole); a change to bleeding.py or
      grip.py touches 2-3 files. Cheap to build (the graph exists), big win on
      the lanes that touch one law.
   4. xdist: -n 4 with --dist loadfile (tests in one file share module-level
      world builds and numba caches; loadscope/loadfile keeps them together).
      Needs: no test writes a fixed filename in the repo (audit for tmp paths:
      grep for open(..., "w") with literal paths), the numba cache dir is
      per-sandbox already (__pycache__ kept in sandboxes), and the
      per-worker memory cap (MemoryMax 2.5 GB x 4 = 10 GB) is lowered to ~2 GB
      with the heavy files marked "serial" (they run in a final -n 0 pass).
   5. Fail fast tier ordering: -x on T0, --maxfail=10 on T1, so a broken base
      does not burn 8 minutes.
COST+RISK
  - Cost: ~1 day (timing file + conftest loader + the affected-tests mapper +
    xdist trial). Risk: tests that secretly depend on order or on shared state
    (module-level worlds mutated by one test) fail under xdist. Mitigation: run
    the suite once under "-n 4" and once under "-p no:randomly -n 0" and diff
    pass sets; fix the order-dependent ones; they are real bugs anyway.
  - Risk 2: heat. The cap.sh cooling gate exists because the CPU hit its throttle
    point under light load. 4 workers will wait on the gate. Real throughput gain
    may be 2.5x, not 4x. Measure before promising.
STATUS: partly scheduled ("fast and slow test tiers", the assistant's item 7;
  EA6 fact goldens). The timing-file, affected-tests and xdist parts are NEW.
PRIORITY: P1. LEVEL: technical.

E2. GOLDEN BIT-HASHES VS FACT GOLDENS (EA6)
======================================================================
EXISTS
  - tools/golden.py: hashes every array and person dict after every tick of ~46
    small worlds (46 in base24), "record on base, check on changed". Frozen
    per-step copy (stepcheck copies golden.py at start). base14..base25 +
    *copy + *_golden.json + *.log in WORK. Wave end: "golden N declared, 0 not
    allowed"; 14b had 17 declared diffs, 14a 38.
  - A hash says "different", never "wrong". Every intended physics change
    becomes a DECLARED diff that a human or agent must justify by name.
PROBLEM
  - Bit goldens are the right tool for pure refactors (the sim.py split) and for
    "this gate is OFF so nothing may change". They are the wrong tool for
    physics work: 17-38 declared diffs per wave means the check is mostly an
    inventory of what changed, and the agents declare them ("small: paid work in
    swings and duels") without anything asserting the new value is RIGHT. The
    declared-diff list is prose in decisions.md, not machine-readable.
  - Cost: recording a base is ~4 min under the lock (stepcheck.sh comment), and
    every lane records or copies its own; golden --all runs on every step check.
  - Bit equality across machines or numba versions is not guaranteed (numba 0.67,
    PYTHONHASHSEED=0 reexec). The hash set ties the project to this laptop's
    float behaviour; any dependency bump forces a full re-record with no way to
    tell a real change from a rounding one.
BETTER
  Split two jobs that are fused today:
   (a) KEEP bit goldens only for "nothing may change": refactors and gate-OFF
       checks (the default for new laws). Keep as is, run at wave end and on
       refactor lanes only, not on every step.
   (b) ADD FACT GOLDENS (EA6): a small JSON per scene of QUANTITIES with
       tolerances and a source or an invariant: peak temperature after N s
       within 2%, total mass drift < 1e-9 relative, energy ledger residual <
       1 mJ, time-to-faint within a band, blood loss rate. A change that moves a
       fact outside its band fails; a change inside the band passes with no
       declaration. Declared diffs become "I moved fact F from X to Y because
       <source>", in a file (tests/facts/<scene>.json with a history array), not
       prose.
   (c) Make the declared list machine-readable now: golden.py check --allow
       takes a comma list; also write the allowed case names, the reason string
       and the lane id to WORK/<wave>/declared.json so the end check can print
       "17 declared, 17 with reasons".
   Where to get the facts: the scenes the golden already steps (46), plus
   tests/data/sourced_numbers.json (exists) which holds sourced values.
COST+RISK
  - Cost: ~2 days for 10 scenes' facts. Risk: tolerances too loose miss a bug,
    too tight make noise; start from the ledger-residual and conservation
    facts (no tolerance argument needed: books must close).
STATUS: EA6 is decided (decisions "ENGINE AUDIT QUESTIONS DONE"); the machine-
  readable declared list is NEW; the "bit goldens only for refactors" rule is NEW.
PRIORITY: P2. LEVEL: technical (the principle, "model real life", already
  favours facts over hashes).

E3. ONE test.lock FOR EVERYTHING; PER-LANE LOCKS
======================================================================
EXISTS
  - WORK/test.lock (empty file, flock target since 2026-10-29). Every pytest,
    golden record/check and stepcheck takes it (tools/stepcheck.sh:105-125;
    gate.sh). A second lock, WORK/lab.lock (nice 19, <= 2 workers), was added
    2026-11-22 after the lab lethal2 run held test.lock for 43+ min and queued
    all five wave-15 batch-1 lanes. Other lock files exist (A_fix.lock,
    A_v2.lock, from Nov 20, dead).
PROBLEM
  - The lock serialises SANDBOXED runs. A lane's stepcheck copies the base to a
    private head/mine tree, so two lanes' checks do not share files or state: the
    lock protects only CPU, memory and heat, not correctness. A global
    mutex for a resource problem is the wrong tool; a long run blocks all
    short ones (the lethal2 case; the wave 15 batch 2 stall).
  - flock has no timeout, no priority, no queue visibility. A lane cannot ask
    "who holds it and for how long"; an agent that waits invents a poll loop,
    which is the pgrep stall in E6.
  - Lock files accumulate (A_fix.lock etc.).
BETTER
  1. Replace the mutex by a small SLOT POOL: N = 2 slots for tests (matches a
     memory budget of 2 x 2.5 GB and one hot core pair each), 1 slot for lab
     (nice 19). Implementation: flock on one of WORK/slots/test.{0,1}, trying
     with "flock -n" in a loop over slots, or "flock -w 1800" per slot, with the
     holder written into the lock file (lane id, command, started-at) so
     "cat WORK/slots/*" shows the queue.
  2. Short runs (T0 and T1 from E1, under 10 min) never queue behind long ones: a
     "short" class with its own slot; full-suite and long lab runs take the "long"
     slot. So a 43-minute run cannot starve a 40-second check.
  3. Lock holder timeout: a holder past a stated budget (the run's own estimate
     x 3) is reported by a watchdog (a cron or the orchestrator), never killed
     silently.
  4. Per-lane PRIVATE lock is meaningless for resource protection; do it by
     classes (short/long/lab) and a slot count, not by lane.
  5. Delete the dead *.lock files.
COST+RISK
  - Cost: half a day: a 30-line "slot.sh" replacing "flock $LOCK" in stepcheck.sh,
    gate.sh, snap.sh. Risk: memory. 2 slots x 2.5 GB cap + 2 lab workers + editor
    on a 14 GB box that currently has 0.7 GB free. Keep the cap, keep the
    temperature gate, start with 2 slots and watch for OOM before raising.
STATUS: lab.lock split DONE 2026-11-22 (decisions log). Slot pool and short/long
  classes NEW. The assistant's item 7 says "per-lane locks": I recommend slots by
  class instead (above), since lanes are already sandboxed.
PRIORITY: P1 (it is what stalled wave 15 b2). LEVEL: technical.

E4. SANDBOXES, SNAPSHOTS AND DISK: STEPCHECK COPIES TOO MUCH
======================================================================
EXISTS
  - tools/stepcheck.sh: head (copy of base) + mine (head + owned paths) per
    step; WORK/<id>/{head,mine}. WORK/snap.sh N: copies src tests tools lab/world2
    lab/judge (excluding tools/blender via "--exclude /blender" at the TOP of the
    rsync) as WORK/base<N> and base<N>copy, 25 MB each; records golden; checks
    fresh. 48 base dirs (base14..25 + copies and more), each 26-28 MB: ~1.3 GB
    in total (small; fine).
  - The "verify" lanes (WORK/<wave>/<lane>_verify/mut, mindL4/*_verify/copy) make
    mutation-test copies of the whole tree.
PROBLEM (measured)
  - 15 directories named "blender" (1.3 GB each) exist under WORK: the mut/ and
    mine/ copies in w13d, w15b2, w14r and others copied tools/blender (a
    third-party 1 GB binary, gitignored). snap.sh excludes it only at the top
    level of "tools/", the rsync in stepcheck "put" excludes only "/blender" at the
    root of the path it is copying: when a lane's owned path is "tools"
    (or "."), the exclude is "/blender" relative to tools/, which works, but the
    verify lanes' own ad hoc cp/rsync commands do not exclude it. Result: ~15 x
    1.3 GB = up to ~20 GB of duplicate Blender.
  - mindL4/*_verify/copy/lab = 13 GB each (copy of lab/vendor 11 GB venvs +
    checkpoints 1.6 GB). mindL4/lethal2_verify and step1_verify alone = 26 GB.
    A verify lane that copies lab/ copies the venvs.
  - w15b2 = 6.8 GB (5 lanes x 1.4 GB: all blender). w13d = 6.1 GB (blender again).
  - WORK totals 62 GB, 88% disk full, 56 GB free: one more careless verify copy
    of lab/ and the disk is the next stall.
BETTER
  1. One shared sandbox builder: tools/sandbox.sh <base> <dest> <paths...>,
     the only way to make a tree copy. It has the exclude list in ONE place:
     tools/blender, lab/vendor, lab/checkpoints, lab/.venv, lab/results,
     renders, __pycache__, *.npz. Both stepcheck.sh and the verify/mutation
     prompts call it; agent prompts say "never cp -r the repo".
  2. Prefer "git worktree" or hard-link snapshots (rsync --link-dest=base<N>)
     instead of full copies: a mine tree that differs in 5 files costs 5 files.
     Cheap, exact, and pycache stays warm if copied per-sandbox (see below).
  3. Mutation-test copies (the "mut" trees) should overlay on top of the lane's
     mine tree via hardlinks and are deleted when the verify lane reports. Put the
     delete in the lane epilogue, not left to a human.
  4. A retention rule, enforced by one script (tools/gc_work.sh), see E9.
COST+RISK
  - Cost: 2-3 hours. Risk: hardlinks mean an in-place edit of a linked file
    changes the base too (rsync writes a new inode by default; "cp -al" does
    not): use rsync --link-dest, which breaks the link on write, never cp -al.
STATUS: NEW. (decisions mention snapshots and "no snapshot of the pre-finish 14b
  state exists", which is the safety side of the same coin, see E7).
PRIORITY: P1 (cheap and frees ~30 GB at once). LEVEL: technical.

E6. WORKFLOW AND AGENT PRACTICES: WHAT WENT WRONG THIS WEEK
======================================================================
EXISTS (from decisions.md and observation)
  1. R4 agent stuck ~4 h in a self-matching "pgrep -f" wait loop; 32 loops
     killed by pid (decisions:361). Lesson recorded as a prompt rule.
  2. Lab chain.sh (pid 1142098) outlived its workflow and held test.lock for 43+
     min; killing it also killed lane 1b's diag.py waits by mistake (decisions:625).
  3. A WORK/coverage folder shadowing a Python package (the owner's report; the
     folder is no longer present in WORK now, so it was removed or renamed).
  4. "pause 14b for now": a lane stopped mid-build left UNVERIFIED PARTIAL edits
     in six or more files of the live tree, and no snapshot of the pre-finish
     state existed (decisions:520-522).
  5. A killed pytest by pid; a lane's runs "queued for hours".
  6. Test files created into the live tree by many agents at once ("several
     agents edit the live tree at the same time", stepcheck.sh header): every
     lane's edits in src/ are visible to every other lane's imports unless it
     checks via stepcheck.
PROBLEM
  - Each is a different symptom of the same causes: (a) agents wait by polling
    process lists; (b) background processes are launched with no owner and no
    deadline; (c) the live tree is shared mutable state; (d) work areas share
    names with import names; (e) "stop" has no protocol.
BETTER (rules and small tools, not prose)
  W1. NO POLLING BY PROCESS NAME. Waits use "flock -w <seconds>" on the slot
      (E3) or "timeout <s> tail --pid=<pid> -f /dev/null" on a pid recorded by
      the launcher. Add a tools/waitfor.sh <pidfile|lockfile> <seconds> that is
      the only sanctioned wait. A deadline on every wait. Put in the agent
      preamble: "never pgrep -f on a string your own command contains".
  W2. BACKGROUND JOB REGISTRY. Every background launch goes through
      tools/job.sh start <lane> <cmd>: writes WORK/jobs/<lane>-<n>.json with pid,
      pgid, command, start, deadline, owner workflow id; runs it under
      "setsid" and "timeout". tools/job.sh ls / kill <lane> kills by process
      group (no stray pid kills like the 1b incident) and the orchestrator
      kills a workflow's jobs when the workflow stops. An expired deadline is
      reported at the next orchestrator turn.
  W3. NAMING: WORK has no top-level folder that equals an importable package name
      (coverage, test, tools, src, lab, docs...). Prefix every WORK dir with its
      wave (w15b2/) and never run python with WORK as cwd or on sys.path. Add
      one line to the sandbox script: PYTHONSAFEPATH=1 (python 3.11+) or
      "python3 -P", so the current directory is not put on sys.path.
      Cheap, kills the whole class.
  W4. PAUSE PROTOCOL. "Pause" = the orchestrator (a) lets running tool calls
      finish, (b) runs tools/checkpoint.sh <lane>, which writes a patch of the
      live tree vs the last base (git diff plus untracked files list) to
      WORK/<wave>/<lane>/PAUSE.patch and a STATE.md listing files touched and
      what is unverified; (c) a resume reads STATE.md. Cost is a git diff.
  W5. EDIT ISOLATION: lanes edit in their own git worktree (E7), not the shared
      tree; the orchestrator merges verified lanes. The shared tree then only
      ever holds verified work, and a pause leaves nothing half-done in it.
      This is the structural fix for item 4 and 6; W4 is the stopgap.
  W6. LANE REPORTS ARE MACHINE-CHECKABLE: each lane's final message includes
      "files touched", "tests run (command + counts)", "declared diffs (ids)".
      The orchestrator diffs "files touched" against "git status" so a file
      touched but unreported (an unverified partial edit) is caught.
COST+RISK
  - Cost: W1-W3 two hours (three small scripts and a preamble). W4 one hour.
    W5 is the real work (a day) and changes how the orchestrator merges.
    Risk of W5: worktrees break the "live tree = base + verified lanes" model that
    stepcheck.sh is built on; merge conflicts show up at merge time, where they
    are cheap, instead of as silent overwrites.
STATUS: lessons recorded as notes (decisions:361, 625); W1-W6 NEW as tools.
PRIORITY: W1-W3 P1, W4 P1, W5 P2, W6 P2. LEVEL: technical.

E11. FASTER FEEDBACK: A DEV LOOP FOR A SINGLE LAW (THE PROPOSAL)
======================================================================
Today a lane's loop is: edit -> stepcheck (copy trees, record or copy golden
base, check 46 cases, run listed tests, all under one lock) = minutes to an hour.
Proposal, in order of leverage:
  1. "make smoke" (E1 T0): 60 s, no lock, no copy, runs in the live tree.
  2. "make law X": runs tests/<law folder or affected set> + the scenes of
     that law in tools/law_timing.py and prints the facts (E2) with their bands.
     Target: 1-3 minutes. This is the loop an agent or the owner lives in.
  3. "make check": T1 (xdist -n 4) + golden on --only the cases whose scene
     touches the changed files (tools/golden.py coverage already maps
     case -> code touched; "golden.py coverage" exists, see its usage header).
     Target: 8 minutes.
  4. "make wave": T2 + golden --all + timing table + base from commit. Wave end
     only.
  The golden "--only <cases that cover the changed lines>" idea reuses
  golden.py coverage (exists) so a one-law change checks 5 cases, not 46.
COST: mostly glue over what exists. Needs E1 and E3 first.
STATUS: partly scheduled (fast tier, fact goldens), the "make" front door is NEW.
PRIORITY: P1 (as the product of E1 and E3). LEVEL: technical.
